# Live Native fixture container correction

The second original live attempt, [44953692820](https://github.com/davidpovarsky/Maktabah/actions/runs/44953692820), built the original application and UI runner successfully. Its genuine miniTest10 installer also passed, including the public compressed asset hash, ten books, 18,879 lines and its managed search artifacts. The live adapter then failed before staging the private input or executing XCTest because it required the fixture database to be inside the application's private data container.

The original application stores this database under `group.com.davidpovarsky.itorah`. `ITorahSharedContainer.resolveSharedRootURL()` asks Foundation for that App Group; the observed native installation and SQL oracle identify its `Otzaria/Profiles/miniTest10/database/seforim.db`. This group container and the application's private data container have different parents. Moving or copying the database would change the original storage contract.

The correction asks the actual Simulator for the installed Maktabah bundle's exact App Group, verifies that it is a direct group container on the same exclusively owned Simulator, and requires the canonical miniature database path and original SHA-256. The oracle must identify that exact file. Post-XCTest verification resolves the current installed App Group again, so private-data or group relocation does not cause an unrelated file to be accepted. Symlink redirection, another device/group, a private-container copy and changed bytes fail closed.

The provider input remains in the application's original private data container. Its permissions, one-use nonce, credential removal from child environments, allowlisted evidence scanning, cleanup and original evidence restoration remain in force. The owned repository secret was deleted after exact metadata verification and its specific API lookup returned 404; the receipt is included. No secret value was read into the audit or published.

Nine new disposable filesystem/CLI-boundary controls passed. Their `simctl` boundary is an explicit test double; they do not prove the Apple CLI or Native execution. The next workflow checks the real `simctl help get_app_container` interface before the build, then the original Native case must still resolve the actual installed group and complete its original assertions. Existing unaffected tests were not repeated. An independent source review found no blocker in the runner at SHA-256 `8891f05b5375fb4c56a426b9cf36b262a7135fb56122cd5b581979073a50d70f`.

The original ZIP, all eleven admitted member hashes, before/after source closure, five code-image identities and cleanup were checked. The application/test source remains `a0781bd2628c1311394f7da6aa1e84c17f252fa4`; this correction changes CI and evidence only. The second attempt provides zero completed provider conversations and no Native116, Release114, device, distribution or live-provider acceptance credit.

Apple's [App Groups entitlement documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups) describes the shared container, and [the Foundation container API](https://developer.apple.com/documentation/foundation/filemanager/containerurl(forsecurityapplicationgroupidentifier:)) explains that its returned URL determines the actual location. The installed Simulator's own CLI help and its resolver output remain the execution evidence for this correction.
