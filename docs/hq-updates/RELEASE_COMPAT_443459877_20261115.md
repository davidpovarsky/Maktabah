## Current route boundaries

- `OtzariaLibraryReleaseClient.parseLatestRelease` recognizes complete monolithic asset names and picks the highest numbered matching name, with the legacy exact-name fallback. Multipart manifests/parts and patch names do not match. Parsing fails before `OtzariaDatabaseBootstrapService` reaches `downloader.download` or `installer.prepare`.
- `OtzariaLibraryRelease` carries **one** asset URL/size/digest. `OtzariaDatabaseDownloader` downloads that single representation with its existing resume sidecar. `OtzariaDatabaseInstaller.prepare` receives one archive URL, extracts it and validates the staged DB before promotion. These are the existing full-database replacement path, not a newly implemented incremental updater.
- `OtzariaZstdStreamExtractor.extractPart` exists and has search-artifact callers. That shared decompression primitive does not supply production-database release-manifest selection, multipart download/assembly, schema acceptance or an update contract. Search remains S-owned and was not edited.
- `BootstrapManager` first calls `OtzariaBootstrapAdapter.restoreForAppLaunch`. That follows local recovery and `OtzariaMaktabahBridge.restoreDatabaseIfPossible` / `OtzariaDatabaseAccessController.restoreIfNeeded`; the valid local path checks local identity/schema and resolves startup ready without fetching latest. This is a static route finding, not a new device-runtime PASS.
- Explicit managed download uses `prepareManagedDatabase` and fetches latest. Its existing catch may resume a validated app-owned cached production partial when strong identity/digest/validator/path checks pass. It does not silently select v32 from release history or make a complete installed DB into a resumable download. No cache was accessed during this audit.
- The schema validator's required-table checks alone do not establish schema-7 engine compatibility. No compatibility claim is made merely because a future monolithic schema-7 filename could match the generic naming rule.
