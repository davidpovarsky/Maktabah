# Whole app exact-occurrence acceptance

This downstream executable compiles the complete production `ActionOccurrenceCoveragePolicy`, `ActionLiveOccurrenceCounter`, original `OtzariaDatabaseAccessController`, artifact/profile/installation models and policy, original Repository and three Swift bridge files, the original SQLite connection, and the original `OtzariaActionCore` package. It links the actual C adapter and original owned-fork Rust engine. It does not substitute SHA-256, engine results, managed coverage, or a qualification registry.

## Evidence and scope

Execution results belong in the run's `verification.json`, `runtime-result.json`, complete logs and source snapshots. Prepared cases do not count as executions. `CASES.json` defines the exact, unique, ordered case inventory. The initial OFF-registry run has 24 cases; the qualified follow-up has 32, with 23 shared cases and nine additional coverage/engine/lifetime cases. These are alternative suites, not 56 distinct tests.

The 24-case run proves rejection with the real empty production registry, complete typed manifest authentication and legitimate re-encoding, 20 nested manifest mutations, canonical scopes, metadata byte/type limits, task cancellation and deadlines, and original selection-owner behavior. One owner case executes 16,000 actual publications concurrently with 24,000 atomic observations and checks the final exact revision. The owner ABA case retains the same URL/source pair but requires a different revision.

The qualified follow-up is permitted only after the separately reviewed production source actually qualifies the original producer/consumer contract. Its command-line `qualification` value is an assertion of expected source state; it never changes that state. Positive cases compare whole app -> original C -> original Rust position counts against a retained independent SQLite oracle for all 18,879 original miniTest10 documents. They also test original book scopes, zero matching occurrences in a known book, multiple-token rejection, source ABA/generation/metadata changes after real native counting, and cancellation/deadline completion while the original engine queue remains held. The published seven index payloads and original DB are hashed before and after execution.

This is Windows source/runtime acceptance. Apple SDK, iOS Native UI, physical-device behavior, Core permission admission, and full-v32 managed app counting are separate gates. The complete original Core types compile here, but the fixture calls the trusted app port directly; it does not claim to exercise the full Core executor's authorization flow. An original full-v32 manifest is authenticated as metadata; no full corpus is copied or scanned here.

## Explicit boundaries

- App bridge boundary: the source generation owner is a locked test shell; its database path comes from the complete original AccessController's real selection observation. No count/result is supplied by this shell.
- Managed storage boundary: resolves only the single owned, verified miniTest10 fixture directory. It does not access user defaults, app containers or user files.
- Index-path boundary: maps that owned database to its copied original index and identity file. Fingerprints use real regular-file size and mtime.
- The complete original AccessController is copied byte-for-byte. `OwnerTestAccess.swift` is appended to that copy so tests can invoke its original private initializer/publication method. The original production file remains unchanged, its exact prefix is verified, and original bytes plus appendix hashes are recorded.
- Bookmark/security-scope/migration/storage-mutation boundaries terminate on unexpected invocation. Owner tests do not call methods that access defaults or persistence. The owner initializer's validator registration is retained; the complete original SQLite class compiles, with only its unrelated unused ZSTD helper trapped.
- UI navigation/rendering shells are compile-only and never provide a result to the Counter. No UI proof is inferred from this executable.
- The optional lexical dictionary URL is absent, matching the explicit exact-token qualification scope. Original required `dictionary.json` and `Acronyms.json` bytes are copied beside the executable and loaded by the genuine Repository if a qualified case explicitly opens its engine.

The original selection owner detects supported publications, including A -> B -> A. The metadata witness detects observed byte changes; this fixture does not claim a filesystem watcher capable of detecting an arbitrary external change and restoration between observations.

## Inputs and dependencies

`prepare-input.py` accepts the already verified immutable miniTest10-v6 receipt, original small DB, and independent SQL oracle. It checks exact expected hashes, creates one UUID-marked owned copy (30,136,393 bytes), checks source and copy hashes again, and records `INPUT_COPY_VERIFIED.json`. It never opens the pristine index. Existing owned copies are revalidated and reused. It does not download or regenerate a corpus.

The actual C static-library build record must report clean fork commit `d5d59d1269bdf87fb0a6901cf31941726a0c699b`; the original index producer remains `265a14ea54f959a3e266d6e8acfa3a3b98101d68`. The driver requires the real compiled artifact hash and clean exact engine checkout. It links the installed Windows SQLite library and records its SDK header identity.

Windows uses the official pinned `apple/swift-crypto` revision `1b6b2e274e85105bfa155183145a1dcfd63331f1` and `apple/swift-asn1` revision `917b472dbe53ba699cbb0495f9a95a084bc6364d`. Actual `Package.resolved`, official origin, checkout HEAD and cleanliness are verified. The existing cache is reused, and compilation uses one job. These are fixture dependencies; app package dependencies and SDK declarations are unchanged.

## Running

Use the recorded complete command from the verified run, supplying the actual build record, pristine exact engine checkout, native-library directory, existing Swift scratch cache, owned input descriptor and a fresh output directory. The driver retains compile/runtime failures, checks all source/resource identities after running, and requires the exact ordered case inventory. Run heavy compiler jobs serially on the constrained host. Never run the historical user-index diagnostics as part of this fixture.
